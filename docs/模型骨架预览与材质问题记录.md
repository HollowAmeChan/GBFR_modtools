# 模型骨架、预览器与材质问题记录

这份文档记录当前奶刀模型替换过程中已经观察到的游戏内差异、可复现结论和后续验证计划。文中明确标注为“假设”的内容仍需要通过预览器、资源对比或游戏帧捕获确认。

## 已确认的骨架结论

- Blender 中静态网格看起来对齐，不代表游戏中的最终位置一致。游戏还会应用骨架初始变换、MOT 动画和其他约束，因此身体、头部在游戏里可能出现脖子断开、头部下插或脚部悬空。
- 当前样本确认 `_000`（hips）是位移锚点。将它吸附或移动到另一套骨架后，身体在游戏中会产生整体高度/位置偏移；把 `_000` 恢复到 source 位置后，身体漂移问题消失。
- 当前样本进一步确认 `_005`（head/neck）也不能移动。它和 `_000` 具有相同的位移骨语义，头部替换时必须保留 source 的静止变换，否则会在游戏动画或运行时约束下造成脖子接不上、头部插入身体等问题。
- `_000` 和 `_005` 的位置不能因为“视觉上重叠”就重新吸附。模型替换应当调整网格、权重和普通子骨骼，保留这两个锚点骨骼的原名、父级和 rest transform。
- 不能因为旧头发或其他部件暂时不用就删除旧骨骼。cloth、SOP、MOT 和权重可能按原骨名或固定索引引用它们；完整模型导出仍应保留 source 骨架，再追加需要的新骨。

## 尚待确认的运行时因素

目前最合理的解释是：动画会给 `_000` 写入角色位移，`_005` 则可能承担头部链的相同语义或被独立的头部动画/约束驱动。需要在预览器中分别观察它们的 rest transform 和动画帧位移，才能区分以下情况：

1. 骨架的 source 初始变换已经不一致。
2. MOT 对 `_000` 或 `_005` 写入了非零平移。
3. 头部使用了独立动画、SOP 或 cloth 约束，导致静态对齐后运行时再次偏移。
4. 网格顶点/权重正确，但模型对象的根变换或分段对象变换没有保持 source 值。

## 预览器已实现

这些功能用于诊断，不应在预览过程中修改导出数据：

- ImGui 视口默认显示 Y=0 地板网格，可单独关闭，用于观察脚部悬空、根骨高度和整体位移。
- 资源表多选不同模型 ID 后会把它们合并到同一场景；同一模型的 `.minfo/.skeleton/.mmesh` 只算一个预览实例，身体 `pl` 排在主实例，头部 `fp` 随后加载。
- 多个骨架共享现有时间轴、播放/暂停、循环和速度。MOT 中能匹配到的头部内部骨骼旋转、缩放和位移会照常播放；但 `fp` 的 `_003/_004/_005` 锚点祖先链不会重复采样身体的同名局部轨道。
- “同步头部动画（`_005` 锚定）”默认开启：先在 `pl` 上完整计算 `_000` 到 `_005` 的动画世界姿态，再让保持自身 rest 链的 `fp` 组件整体对齐到身体 `_005` 的位置和朝向。`pl1400` 与 `fp1400` 只共享 `_003/_004/_005/_a04`；面部骨大量从 `_003`、`_004` 分叉，并非都位于 `_005` 以下。如果先在 `fp` 上再次写入 `_003/_004/_005` 的局部 Euler，再做 `_005` 校正，锚点本身虽然重合，上层分叉却会得到反向补偿，表现为头部跟随但旋转方向错误。当前实现让身体链只计算一次，校正作用于整个 `fp` 骨架组件，同时保留非锚点共享骨的相对动画；不会写回 `source`、`unpack`、`build` 或 Blender 文件。
- 模型预览默认关闭背面剔除，单面网格的正反面都会显示；需要检查真实绕序、反面或材质单面效果时，可以手动开启“背面剔除”。该开关只影响预览器光栅状态，不会修改 mmat。
- “位移锚点诊断”表显示每个模型 `_000`、`_005` 的文件 rest 位置、当前帧位置、差值和联动状态。
- 预览控制区逐项显示所用 `.minfo`、材质 JSON 与 SOP；动画、SOP 和 cloth 仍以主 `pl` 模型为运行上下文，不会从 `build` 读取。

### 预览左右手性结论

曾观察到新导出的 `pl` 在 C++ 预览器中左右相反，但 Blender 与游戏内正常。最终确认这是预览相机问题，不是 MOT、顶点顺序或 Blender 导出文件被镜像：

- `希罗处理/输出.blend` 中实际导出候选 Mesh 和 Armature 均为 `location=0`、`rotation=0`、`scale=1`，世界矩阵行列式为 `+1`，不存在对象级负缩放或镜像。
- 奶刀 `source` 与 `unpack` 的刀鞘分段原始 X 坐标一致；Blender 插件导入与导出也都直接读写 XYZ，没有额外交换 X 轴。
- 旧预览器把相机放在模型 `+Z`，却使用 `XMMatrixLookAtLH/XMMatrixPerspectiveFovLH`。相机朝 `-Z` 时，其屏幕右方向对应世界 `-X`，因此刀鞘等非对称参照会显示在相反一侧。
- C++ 编辑器的模型预览只读取 `unpack`；此前所谓“source 正常、导出文件反向”并不是在同一渲染器中的 A/B 对比，而是 Blender/其他查看器与 C++ 预览器之间的对比。近似对称的 `fp` 面部也不足以证明左右方向正确。

预览器现统一使用右手视图和投影，并同步调整正面绕序、水平 orbit 符号与 Shift 水平平移基向量。四者必须一起修改：只把 LH 矩阵换成 RH 会让模型左右恢复，却会造成鼠标旋转和平移方向相反。修复不再按 skeleton magic 区分官方或 Blender 导出模型，也不会镜像网格、骨架、MOT 或任何磁盘文件。

今后判断导出是否镜像，必须把 `source` 与 `unpack` 送入同一套加载器、相机姿态和投影后，再使用刀鞘、单侧配饰或明确的左右骨骼作比较；不能用两个查看器的屏幕结果直接推断二进制数据发生了镜像。

## 材质与贴图待办

- 已确认工作区 `source` 是 GBFRDataTools 2.0.0 完整解包结果；本仓库旧 `A1/A2/A4` 占位 schema 无法正确表达新版字段及带浮点池的材质。现已替换为正式 2.0.0 schema，并加入独立 mmat 检查器、旧 JSON 构建保护和新版 Granite 引用处理。奶刀 `pl1400/fp1400 vars/0` 的旧 build 常量缓冲与索引仍和 source 一致，不能把当前发黑直接归因于旧封回；后续要按材质槽比较实际投放文件。已有工作区仍需对每个 mmat 执行一次“从 source 重新解码 JSON”，详见 [MMAT 材质格式与 ER 升级](formats/MMAT材质格式与ER升级.md)。
- 单面材质的透明效果还没有在编辑器中提供独立控制。需要明确区分背面剔除、双面渲染、alpha blend 和 alpha clip，并在材质编辑界面提供可保存到 mmat 的设置。
- 贴图封回与预览的颜色空间、法线格式和 Granite/普通 `.texture` 路径需要继续按材质类型核对；“预览正常”不能单独证明游戏内材质状态正确。

## 平整表面毛躁/噪波

观察到模型平整表面进入游戏后，在某个方向出现明显毛躁噪波；沿着模型与世界原点连线的方向不明显，接近垂直方向时更明显。目前不能把它归因于单一问题，优先排查：

- 法线、切线或 bitangent 的方向/手性在导出后与 source 不一致。
- 法线或切线缓冲的量化、归一化或顶点拆分造成平面上的微小不连续。
- mmat 中的法线贴图、roughness、镜面参数或颜色空间解释不正确。
- 蒙皮后法线变换、对象根变换或 LOD 切换导致方向相关的闪烁。
- 游戏的镜面高光、TAA 或阴影采样放大了上述微小误差。
- MMAT Metal-family 参数 `0xA6EB1B34` 已确认只在角色样本的 `shadow_type=3 / bool12=true` 状态启用。游戏按 `0.6 - 0.4 * dot(归一化根/对象位置方向, 对象向量)` 生成动态 Alpha 裁切阈值；对象向量为单位方向时标称范围是 `0.2..1.0`。已反汇编的 Metal `5discard` 和 depth-only pass 会用它丢弃像素。若毛躁只出现在灰度 Alpha 边缘，这是首要候选；若完全不透明区域也毛躁，它不能解释该现象。

### 已确认的数据缺陷：uint16 权重量化未闭合

当前毛躁现象与摄像机方向无关，异常顶点稳定地沿角色到世界原点的方向偏移。对 Blender、实际投放的 `build`、官方 source 和 RenderDoc 顶点着色器交叉检查后，确认旧导出器存在必须修复的权重格式违约：

- Blender `pl1400.004` 的浮点权重已经归一化。`common` 全部顶点的最大总和误差只有 `4.84e-8`，裙子顶点只有 `4.47e-8`，不是 Blender 权重本身超 1 或缺权重。
- `.mmesh` 每个 influence 使用 `uint16`，游戏输入为 16 位归一化权重，精度是 `1/65535`。旧导出器对每个分量独立执行 `round(weight * 65535)`，没有在量化后补齐总和。
- 实际投放的 `build/unpack` LOD0～LOD3 使用同一组 49,011 顶点权重：44,097 个总和为 `65535`，2,519 个为 `65534`，2,395 个为 `65536`。没有零和顶点、无效 deform 索引或超界索引，但共有 4,914 个顶点违反严格闭合契约。
- 受 `Skirt*` 骨影响的 3,896 个顶点中，535 个欠 1、581 个多 1；欠/多权重顶点遍布完整裙面而非只在边缘，符合平整面上随机毛躁的空间分布。
- 官方 source 的 LOD0 56,296、LOD1 81,747、LOD2 41,099、LOD3 9,962 个顶点全部严格等于 `65535`，四个 LOD 没有一个例外。这证明游戏资产管线要求量化后的整数权重严格闭合。

RenderDoc `frame3216` 的角色主体 draw `EID 18799` 使用 VS `ResourceId::58268`。DXBC 指令 1～29 直接用 `BLENDWEIGHT` 的四个分量混合 `g_InstanceWorldTbl` 中三行 `float4` 骨矩阵，包含每行 `.w` 平移；着色器没有计算或除以权重和。位置以 `float4(position, 1)` 与混合矩阵点乘，之后才把结果的齐次分量设回 1。因此：

- 总和 `65534` 会少混入 `1/65535` 的共同世界平移，使顶点沿世界原点方向偏移。
- 总和 `65536` 会多混入 `1/65535` 的共同世界平移，使顶点反方向偏移。
- 偏移量与角色离世界原点的距离成正比；同一个模型和姿态下，异常顶点集合固定，不随摄像机变化。

本仓库预览 shader 曾执行 `position = skinnedPosition / weightSum`，会把这类误差除掉，所以预览平整而游戏毛躁并不矛盾。预览器的归一化只能作为显示容错，不能代替磁盘格式契约。

Blender 插件导出器现改为对一个顶点的全部正权重统一量化：保留总和已经位于 `1±1e-6` 内的 Blender 归一化浮点值，只对真正未归一化的输入重新归一化；随后逐分量四舍五入，并把与 `65535` 的整数差值补到量化后权重最大的主 influence，强制整数和严格等于 `65535`。容差与整数主权重补偿不会被重复 LOD 之间几 ULP 的浮点差异扰动。零权重顶点会阻止导出。该修复的目的不是美化数据，而是恢复游戏 VS 明确依赖的齐次变换不变量；后果是所有旧 `65534/65536` 顶点的权重字节及 `.mmesh` 哈希都会改变。

已有 `unpack/build` 不会自动修复。必须用更新后的插件重新导出 `pl1400.004`，重新构建并投放全部 LOD，再进行游戏内 A/B 验证。禁止只修改单个裙骨、少量可见顶点或单个 LOD；权重缓冲按整个 LOD 共享，局部处理会留下同类错误并破坏对照结论。

### 实验性新增骨命名与 Bone Collection

对当前制作文件 `希罗处理/输出.blend` 的活动身体骨架 `pl1400.004` 和已写入 `unpack` 的 skeleton 逐项核对后，确认旧实验导出具有以下行为：

- source skeleton 有 342 根骨，`pl1400.004` 有 838 根骨；496 根新增骨全部按 Armature 原生顺序追加，旧分配器把它们全部放进纯数字区 `_016`～`_558`。前发、后发、袖子和裙子分别落入不同数字段，但分配器没有根据权重、父级或部件语义分类。
- 旧映射中，`HairFrontSide_*` 位于 `_018`～`_114`，`HairSide_*` 位于 `_115`～`_138`，`HairBack/HairBackEX_*` 位于 `_139`～`_279`，`HairFront_*` 位于 `_280`～`_300`，`Sleeve_*` 位于 `_315`～`_351`，`Skirt/SkirtSide_*` 位于 `_352`～`_535`。范围中的空洞是 source 已占用的身体/手指编号。
- 数字区具有身体骨语义；`_axx` 大量用于受 SOP 等约束驱动的 Deform/Twist/Corrective 或服装骨；当前样本中的 `_cxx/_dxx` 更接近相对独立、无 SOP 约束的头发和服装辅助骨。曾据此把实验分配顺序改为 `_cxx`、`_dxx`、`_axx`、纯数字区，数字区只作为最后回退。
- `pl1400` source 已占 73 个 `_cxx`、111 个 `_dxx` 和 84 个 `_axx` 名称；临时新顺序把当前 496 根新增骨实际分配为 `_cxx` 183 根、`_dxx` 145 根、`_axx` 168 根，数字区为 0 根。重新导出并进游戏验证后，毛躁没有任何改善。因此“新增骨落入数字身体区，或骨名首字符分区触发特殊处理”已排除；插件已恢复原实验顺序 `_xxx`、`_cxx`、`_axx`、`_dxx`。

Blender Armature 的 Bone Collection 也会被当前导出器写进 `.skeleton`，并非只用于视口整理：

- 导入 source 时，`Bone.A1.Unk` 被还原为 `_0/_1/_2/_3/_4/_5/_9/_a/_c/_d` 等 Bone Collection；导出时集合名再次编码为最多四字节 ASCII 写回 A1。
- 用户自建的 `_h/_v/_s/Humanoid` 同样会写入游戏文件，其中 `Humanoid` 被截断成 `_Hum`。这些自定义值尚未证明属于游戏认可的骨骼分组契约。
- 当前导出的新增骨 A1 分布为：头发 `_h` 249 根、袖子 `_v` 34 根、裙子 `_s` 166 根，其余主要为 `_a` 和 `_Hum`。同一骨骼属于多个集合时，导出器使用集合遍历中最后命中的值；没有集合时不写 A1。
- 前发和后发都属于 `_h`，因此自定义 A1 是必须隔离验证的风险，但不能单独解释“前发毛躁、后发正常”。本次已排除的只是骨名分区；临时新顺序没有改变 A1。后续验证 A1 时应保持骨名、索引、父级、rest transform 和权重不变，只把新增骨 A1 统一为 source 已存在的分组，避免同时改变两个变量。

建议按以下顺序验证：

1. 对同一平面区域逐顶点比较 source 与导出 mesh 的 position、normal、tangent 和 UV。
2. 在游戏中临时关闭法线贴图和镜面/roughness，确认噪波是否消失。
3. 改变模型朝向、相机方向和世界位置，判断噪波是随模型、光照还是世界原点方向变化。
4. 在预览器增加 normal/tangent debug 显示；必要时使用游戏帧捕获确认最终 GPU 输入。

## 当前操作原则

- 替换身体、头部或其他分段时，保留 source 的 `_000`、`_005` 以及全部原骨架层级；不要移动这两个位移锚点，也不要为了清理旧部件删除可能被 cloth/SOP/MOT 引用的旧骨。
- 先在多 mesh、多骨架联动预览中确认静态接缝和动画接缝，再将 `.minfo`、`.skeleton` 与所有相关 `.mmesh` 作为一组构建到 `build`。
- 任何尚未证实的材质或噪波原因都应记录为假设，并保留 source 资源用于逐项对比。
- 不能删除骨骼，目前的导出器不支持删除原有的骨骼导出
