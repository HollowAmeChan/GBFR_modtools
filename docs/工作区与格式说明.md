# 工作区与格式说明

本文记录 C++ 编辑器的角色工作区流程，以及贴图、材质、动画和 cloth 格式的已验证发现。源码环境见 [构建与开发](构建与开发.md)，代码边界见 [C++ 架构](架构.md)。

模型与骨架的 Blender 流程见 [模型与骨架 Mod 制作流程](模型与骨架Mod制作流程.md)；`_aXX` deform/corrective 骨的平行骨链和 SOP 后处理见 [SOP 骨骼后处理与 Deform 骨](formats/SOP骨骼后处理与Deform骨.md)。

## 准备

双击根目录 `build.bat`。脚本会自动下载、校验并安装 `GBFRDataTools/flatc/GraniteTextureReader/texconv` 到 `_lib/tools/`，不再要求用户手工复制 EXE。工具版本与哈希见 [构建与开发](构建与开发.md#自动依赖)。

## 1. 生成角色工作区

在编辑器开始页选择角色主体 `.minfo`，并在下一行指定工作区输出目录。例如：

```text
data/model/pl/pl1400/pl1400.minfo
```

输出目录留空时回退到工具根目录的 `explore_output`。指定其他目录后，每个目录都可作为独立工程长期保存；抽取期间开始页下方的“抽取控制台”会实时显示扫描、复制、解码和错误输出，完成后不再等待按键，并自动打开该目录中的 `workspace.json`。工具会扫描主体以及相同数字 ID 的 `fp`、`wp` 资源，并重建所选目录：

```text
<所选工作区>/
  manifest.md                 人类可读的资源与约束报告
  workspace.json              路径映射与初始文件哈希
  source/data/                原始资源副本，只作封包模板
  unpack/data/                可编辑的 DDS、JSON、XML 与模型二进制
  build/data/                 最终 Mod 输出
```

探索器会自动完成：

- 按游戏的 `data/...` 路径复制找到的资源。
- 将 `data/texture/{2k,4k}/*.texture` 解码为 DDS。
- 按角色 ID 收集 `ui/fhd/layouts/common` 和 `ui/layouts/common` 下的角色专属 WTB：状态头像、对话头像、角色立绘、奥义链图和配色预览；解码后的 DDS 位于同一 `unpack/data/ui/...` 原路径，编辑器中单独归类为 `UI-image`。
- 根据 mmat 的 `granite_params.page_file` 哈希，从 `data/granite/{2k,4k}/gts` 提取 `albd/msk1/msk2/nrml` 以及眼球的 `conj/iris/eyeh` 分层贴图，并转换为 DDS。
- 将 `data/model/**/vars/*.mmat` 解码为 `*.mmat.json`。
- 将角色 cloth 基础组、碰撞体、动作覆盖和重置表解码为 `*.bxm.xml`。
- 将身体 `.mot` 复制到 `source/data/pl/<角色>/`，并将同数字 ID 的表情骨骼 `.mot` 复制到 `source/data/fp/<面部>/`，供 C++ 预览器按需解码；动画不会复制到可编辑的 `unpack`，也不会进入 Mod 构建列表。
- 解析 pl/fp/wp 模型同目录的 `.sop`，在 `manifest.md` 中生成逐骨、逐操作的动画约束表，并把包含原始属性的结构化结果写入 `workspace.json/SkeletonConstraints`。报告分别标注“已探明、部分探明、未探明”和“预览器是否实现”，不会把作用推断当成完整公式。
- 身体与对应头部的 `.mot` 会登记到 `workspace.json/AnimationFiles`。每条记录明确保存 `ModelId`、source 基线、Blender 可写的 unpack 输入、build 输出和两份基线哈希；Blender 写出的原生 MOT 不需要再次编码，编辑器构建时会原子复制到 build。
- 将 pl/fp/wp 的 `.minfo`、`.skeleton` 与所有已存在的 `lod#`/`shadowlod#` `.mmesh` 原样复制到 `unpack`，登记为可恢复、可构建的模型文件。
- 记录中间态 SHA-256，用于识别真实修改。

Granite DDS 输出到 `unpack/data/granite/{2k,4k}/`，格式为：

- `albd`：BC7 sRGB，DX10 头。
- `conj`、`iris`、`eyeh`：BC7 sRGB，DX10 头。
- `msk1`、`msk2`：BC7 线性，DX10 头。
- `nrml`：BC5 UNORM 线性，DX10 头。

转换时会生成完整 mip 链。某些 Granite page hash 在当前游戏数据中没有对应 GTP，探索器会把它们记入 `workspace.json` 的 `GraniteMissing`，其余贴图继续处理。

### 眼球与瞳孔贴图

眼球材质不是普通的单张 `albd`。以 `fp1400` 的默认材质为例，左右眼各自通过 mmat 的 `texture_maps.texture_name` 和 `granite_params.page_file` 引用多层贴图。编辑器预览会按 alpha 合成 `conj + iris + eyeh` 三个颜色层，`msk1` 作为独立的线性遮罩保留：

- `*_conj`：眼白、结膜和眼球底色。
- `*_iris`：虹膜与瞳孔；修改瞳孔形状、大小或眼睛颜色时主要编辑这一层。
- `*_eyeh`：眼球高光和反光形状。
- `*_msk1`：眼球使用的线性遮罩，不是基础色；左右眼可能共享同一张 `msk1`。

制作眼睛贴图时，应保留 `conj/iris/eyeh` 的透明通道，因为分层合成依赖 alpha。颜色层使用 BC7 sRGB，`msk1` 使用 BC7 线性；不要把 `msk1` 当作缺失的 albedo，也不要只用一张普通 albedo 覆盖整只眼睛。DirectX DDS 在编辑器预览时会统一翻转 V 方向，制作内容时不需要额外手工倒置图像。

面部透明不能只看 `shader_sub_type`（旧 schema 中显示为 `A7`）。Alpha 相关参数位于 `shader_params`，其中 `0x53F49792` 在编辑器中显示为 `Cutout 丢弃模式`，它选择 `_5discard` 变体，不是半透明开关；同时还要核对 `shadow_type`、`ignore_alpha`、`g_IsUseAlbedoAlphaClip` 和 `g_EnableDiscardMask`。以 `fp1400` 为例，主面部 subtype 7 与承载牙齿、舌头的未遮罩 subtype 5 都在不透明 pass 中按 `face_albd.A` 裁切并写深度；眉毛、睫毛覆盖层才使用 `face_albd.A * face_msk2.B`，以 `0.2` 阈值去掉 BC7 低灰噪点，并在不写深度、带深度偏移的透明 pass 中绘制。制作眉毛或睫毛时，应同时检查 albedo alpha 与 msk2 蓝通道，并保持 msk2 为线性数据。视口的“透明覆盖”只控制已确认的 `msk2.B` 覆盖层，不会关闭主面部或口腔实体必须执行的 albedo alpha 裁切。

| 面部材质路径 | mmat 判定 | Coverage | 深度与光栅状态 | 用途 |
| --- | --- | --- | --- | --- |
| 主面部 clip | `shader_params/0x53F49792 != 0`，非透明覆盖层；该参数选择角色 pass key `0x4` 的 `_5discard` 变体 | `albd.A` | 不透明 pass，写深度，背面剔除 | 裁掉面部 atlas 中不属于皮肤表面的区域 |
| 口腔实体 clip | alpha 开启、subtype 5，但不属于 `msk2.B` 覆盖槽 | `albd.A` | 不透明 pass，写深度，背面剔除 | 牙齿、舌头等必须按真实几何深度互相遮挡的口腔内容 |
| 遮罩覆盖 | alpha 开启、subtype 5，常量缓冲指向面部覆盖槽 | `albd.A * msk2.B` | alpha blend，不写深度，双面并带深度偏移 | 眉毛、睫毛等贴在脸表面的共面覆盖 |

当前渲染顺序固定为主面部与口腔实体 clip、遮罩覆盖，最后才绘制骨架和碰撞调试线。这里把“裁切”和“混合”分开处理：主面部即使关闭“透明覆盖”也必须继续执行 alpha clip；否则 albedo atlas 的深色无效区域会在眉毛两端显示为黑色三角。口腔实体也必须写深度；把它当成普通透明层会让牙齿、舌头和口腔壁按提交顺序互相覆盖。遮罩覆盖则不能写深度，否则眉毛等共面层会与脸部发生闪烁或随视角消失。

使用编辑器快捷操作删除眼球材质条目的 `granite_params`、改用 `data/texture` 下的普通 `.texture` 时，需要同时构建该材质 `texture_maps` 实际引用的 `conj/iris/eyeh/msk1` 文件；只编码 `iris` 而把其余层留在 Granite 中，不能保证清除 Granite 配置后仍能得到完整眼球效果。默认配色只处理 `vars/0.mmat.json`；其他配色仍需在对应编号的 mmat 中分别处理。

正式网格统一从 `data/model_streaming/lod*/` 收集。为了让 Blender 导入器工作，用户有时会把 LOD0 `.mmesh` 手动复制到 `.minfo` 同目录；探索器会在报告中标记这种辅助副本，但不会将它复制到 `source`，避免与正式流式网格重复。

玩家角色只会按相同数字 ID 自动关联 `fp` 面部/头部与 `wp` 武器资源。`fn` 和 `np` 都是其他独立 NPC 的资源，不属于该玩家角色，因此生成 `pl` 工作区时不会收录它们的模型、流式网格、材质或贴图。只有在开始页明确选择 `fn*.minfo` 或 `np*.minfo` 时，才会将其作为独立资源生成工作区。

生成操作会完整重建本次选择的工作区目录，执行前会显示实际路径并要求确认。要同时保留多个角色或多个修改方案，为每次抽取选择不同目录；不指定目录时才会反复使用并重建默认的 `explore_output`。

### UI-image 路径与封回

路径规则参考 [Relink Modding Wiki 的 Asset Paths](https://nenkai.github.io/relink-modding/resources/asset_paths/)。

UI 角色图不是模型 Granite 贴图。官方资源树将它们放在 `ui/layouts/common/*/noatlastextures/`，`ui/fhd/` 对应 1080p，去掉 `fhd/` 的同路径对应 4K。以 `pl1400` 为例，探索器会按文件名精确匹配：

```text
cmn_chrprm_1400_*.wtb       状态/小头像
cmn_chrvo_pl1400_*.wtb      对话头像
cmn_imgchr_1400*.wtb        角色立绘
cmn_imgchain_1400*.wtb      奥义链图
cmn_imgcol_pl1400_c*.wtb    配色预览
```

这些 WTB 的 DDS 槽解码到 `unpack/data/ui/...`，列表类型显示为 `UI-image`，不会和 `贴图槽` 合并。编辑 DDS 后，在 Inspector 使用“封回 WTB 到 build”；编辑器以 `source/data/ui/.../*.wtb` 为模板写入 `build/data/ui/.../*.wtb`，并保留 WTB 的槽索引。使用“从 source 恢复 DDS”只恢复该 WTB 登记的 DDS 槽，不会修改 `source`。通用 `ui/atlas` 图集目前不按角色自动拆分，因为它需要额外的 sprite 区域表；若要替换图集，应作为独立 UI 资源处理。

## 2. 编辑

只编辑 `unpack/data/`：

```text
unpack/data/texture/2k/foo_0.dds
unpack/data/texture/4k/foo_0.dds
unpack/data/granite/2k/foo_albd.dds
unpack/data/granite/4k/foo_nrml.dds
unpack/data/model/pl/pl1400/vars/0.mmat.json
unpack/data/model/pl/pl1400/pl1400.minfo
unpack/data/model/pl/pl1400/pl1400.skeleton
unpack/data/model_streaming/lod0/pl1400.mmesh
unpack/data/pl/pl1400/cloth/pl1400_0_0_clp.bxm.xml
unpack/data/pl/pl1400/pl1400_0002_0_seq_edit_cloth.bxm.xml
```

`source/` 是不可编辑的原始模板。删除 `unpack/` 中间文件后，该项会标为“缺少输入”。当前 C++ 版本已支持模型 `.minfo/.skeleton` 和全部已登记 `.mmesh` 的逐项恢复；点击具体 `.mmesh` 会按其 `lod#`/`shadowlod#` 层级预览，其他中间态的原生恢复命令尚未迁移。

Blender 插件的“导出到工作区”会让用户选择 `workspace.json`，在确认前列出当前模型对应的 `.minfo`、可选 `.skeleton` 和全部 LOD `.mmesh` 目标，然后由 v2 构建器直接覆盖 `unpack`。不再需要管理 `_Exported_MInfo`、手动复制文件、调试 JSON 或 `flatc.exe`；`build` 仍只接收在编辑器中确认后的最终文件。

### 预览数据来源

预览器不会读取 `build`，也不是只读取单一目录。当前模型预览按数据职责组合以下来源：

| 预览内容 | 来源 | 原因 |
|---|---|---|
| `.minfo/.skeleton/.mmesh` | `unpack` | 显示用户正在编辑的模型结果 |
| `vars/0.mmat.json` 与 DDS | `unpack` | 显示默认配色的编辑中间态 |
| CLP/CLH 与动作 cloth 覆盖 XML | `unpack` | 显示当前物理参数编辑结果 |
| `.mot` 动画 | `unpack` / `source` | 默认检查 Blender 写入的编辑结果，也可切回原始基线对照 |
| `.sop` 约束 | `source` | 作为只读的动画后处理定义 |
| `build` | 不读取 | 只保存准备投放的最终 Mod 文件 |

视口顶部会显示当前模型或贴图以及各组成数据的来源。动画栏提供 `unpack` / `source` 来源切换和各自文件数量，选择后显示当前 MOT 与可选 cloth 覆盖的实际来源；鼠标悬停来源标记可查看具体相对路径。

### 动画预览

C++ 编辑器会为当前已加载的所有模型组件同时扫描 MOT：身体读取 `unpack/source data/pl/<角色>/*.mot`，头部读取 `unpack/source data/fp/<面部>/*.mot`。因此同时预览 `pl + fp` 时，身体动作与 Blender 导出的面部动画会出现在同一播放列表；工作区 `AnimationFiles` 登记的自定义输入路径也会纳入列表。`fp` MOT 是实际驱动眼睛、眉毛、嘴部等面部骨骼的表情切片。动画栏默认选择存在文件的 `unpack`，可随时切到 `source` 做基线对照；Blender 在预览器启动后写出 MOT 时，点击顶部“刷新”或动画栏“重新扫描”即可发现。视口顶部可以按文件名筛选、选择、播放/暂停、回到开头、循环、调整速度或拖动时间轴；选择“静止姿态”会恢复绑定姿态。多模型场景中，同一骨骼编号的轨道会同时应用到每套骨架，并可通过默认开启的 `_005` 联动把头部骨架组件吸附到身体锚点。动画预览不会修改 `unpack`、`source` 或 `build`。

`*_seq_edit_facialmotion.bxm` 记录身体动作时间轴在何时切换哪一个 `AnimationNo/AnimationType` 表情，它不是表情顶点数据本身。当前编辑器先提供 fp `.mot` 切片的直接选择和播放，还没有把身体动作与该调度表自动合成为一条时间轴。

`.mot` 使用 60 FPS 帧时间。动画记录中的骨骼 ID 不是 `.skeleton` 数组下标，而是十六进制骨骼名编码，例如 `0xC45 -> _c45`；对象级 `-1` 轨道映射到各骨架组件的根骨 `_900`。当前解码器支持样本中出现的压缩类型 `0-8`，并将位置、欧拉旋转和缩放轨道应用到本地骨骼姿态。CPU 只计算层级姿态和最多 1024 个蒙皮矩阵，顶点位置与法线由 GPU 顶点着色器实时蒙皮，不再为每帧动画重写整份顶点缓冲。解码器独立位于 `include/gbfr/formats/animation.hpp` 与 `src/gbfr_formats/src/animation.cpp`，可以脱离编辑器 UI 复用。

当前预览一次只播放主模型选择的一个骨骼动画切片；多选模型共享该切片和时间轴，但尚不处理游戏状态机、切片混合、身体/表情自动联播、IK 或动画驱动的 cloth 参数。未知辅助属性会被保留在解码结果中，但不会错误地套到骨骼 TRS 上。

身体 skeleton 中 `_aXX` 组不是普通动画骨：`.mot` 不包含它们的轨道，游戏会在动画采样后使用模型同目录的 `.sop` 从上臂、大腿等正常骨派生其 swing/twist 与 corrective 姿态。它们故意挂在驱动骨的上一级形成平行骨链，不能只按 skeleton 父级继承。完整结构和公式见 [SOP 骨骼后处理与 Deform 骨](formats/SOP骨骼后处理与Deform骨.md)。

### `vars/*.mmat` 编号与配色

`vars/0.mmat` 是角色默认配色使用的完整材质配置。`vars/1.mmat` 到 `vars/10.mmat` 是其他配色的并列完整配置，并不是继承 `0.mmat` 的差异补丁。

不同编号通常保持相同的材质条目、Shader 参数、法线和遮罩，只替换需要变色部件的 albedo 与对应 Granite hash。例如：

```text
vars/0.mmat   -> pl1400_body01_lod0_albd
vars/1.mmat   -> pl1400_body01_lod0_c01_albd
vars/2.mmat   -> pl1400_body01_lod0_c02_albd
...
vars/10.mmat  -> pl1400_body01_lod0_c10_albd
```

并非每个部件在所有配色中都会变化；皮肤、部分刀鞘或某些配色下的头发仍可能引用基础贴图。以 `pl1400` 为例，主体 `pl` 与面部 `fp` 都有 `0–10.mmat`，武器 `wp` 只有 `0.mmat`。

- 只修改默认配色：编辑 `vars/0.mmat.json`。
- 希望所有配色使用相同材质逻辑：同步检查并修改 `vars/0–10.mmat.json`。
- 删除 `granite_params`：必须在希望生效的每个编号中分别删除；只修改 `0` 不会影响其他配色。
- 多个编号引用同名 nrml/msk 时，共享 DDS 可以只生成一份，但每个编号的 mmat 引用仍独立生效。

#### 统一所有配色并复用默认贴图

如果 Mod 的设计目标是让角色的所有配色都显示成同一套外观，可以把同一模型的 `vars/0.mmat` 完整复制为其他编号的 mmat。游戏选择配色时仍会加载对应编号的文件，但这些文件内容相同后，所有配色都会使用 `0.mmat` 中相同的材质条目、Shader 参数、渲染状态和贴图引用。因此无需为每个配色重复制作和发布 `_c01`、`_c02` 等贴图。

已经检查过一个实际发布的 `pl0400` 角色替换 Mod：其中 `vars/0.mmat` 到 `vars/8.mmat` 的 SHA-256 完全相同，九个文件都引用无配色后缀的同一组 `pl0400_skin_lod0_*` 贴图，Mod 中也只发布了这一组皮肤贴图。这证明“保留每个配色编号的 mmat 文件，但让内容和贴图引用统一”是可用的发布方式。

最终 Mod 可以直接复制二进制文件：

```text
data/model/pl/pl1400/vars/0.mmat -> 1.mmat ... 10.mmat
data/model/fp/fp1400/vars/0.mmat -> 1.mmat ... 10.mmat
```

使用编辑器工作区时，复制 `unpack` 中同一模型的 `0.mmat.json` 内容到其他编号的 `*.mmat.json`，再分别构建这些 mmat。也可以在每个变体材质中只把目标 `texture_name` 改回无 `_cNN` 后缀的默认贴图名；后一种方式能保留其他配色专有的 Shader 参数和特殊贴图。

使用这项优化时必须遵守以下边界：

- 不能删除 `1.mmat` 到 `10.mmat`；游戏会按当前配色编号加载对应文件，缺失时不会自动继承 `0.mmat`。
- `pl`、`fp` 和存在配色变体的 `wp` 是独立模型，必须在各自目录内分别处理，不能把身体的 mmat 复制给面部或武器。
- 完整复制 `0.mmat` 会同时覆盖该配色的全部材质差异。以 `vars/10.mmat` 为例，独立的 `_c10_emsv`、`_c10_msk1` 和特殊发光参数也会丢失；需要保留这些效果时，只修改希望复用的 albedo/face/iris 等贴图引用。
- 身体与面部可能分别切换 body、hair、face、iris 等贴图。只统一 `pl` 而不处理 `fp`，仍会留下脸部或眼睛的配色差异和对应贴图依赖。
- 只有确认全部 `vars/*.mmat` 都不再引用某个 `_cNN` 贴图后，才能从发布包删除该贴图。应同时检查所有模型类型和 `2k/4k` 输出。

这种方法减少的是重复贴图和逐配色编辑工作，编号 mmat 本身仍要保留。若所有配色本来就应该完全一致，完整复制 `0.mmat` 最省事；若要保留十号发光、特殊眼睛或局部配色，则应使用编辑器逐项统一贴图引用。

Granite DDS 是可编辑中间态，编辑器不会修改 GTS/GTP。需要增加普通贴图（包括自定义面部描边遮罩）时，把 DDS 放进 `unpack/data/texture/2k` 或 `unpack/data/texture/4k`，不要放进 `unpack/data/granite`。文件名使用 `<贴图名>.dds` 或 `<贴图名>_0.dds`；点击工作区“刷新”后会显示为“手动 DDS”，无需修改 `workspace.json`。mmat 的 `texture_name` 只填写 `<贴图名>`，不带目录、`_0` 和文件后缀。构建输出为 `build/data/texture/<分辨率>/<贴图名>.texture`。同名输出已被工作区其他资源占用时不会重复登记。

“手动 DDS”和从 Granite 解码的新贴图使用同一条普通 `.texture` 新建流程。`unpack` 中统一采用 Paint.NET、Blender、Substance Designer 与 Granite 解码图所见的顶左编辑方向；构建器会在封装前执行垂直翻转（V 向翻转），并对全部 mip 生效，以匹配游戏中普通 WTB payload 的储存方向。mmat 检查器的“贴图与 Granite”页可以从工作区贴图名列表填充空引用、修改现有引用、添加常用 Shader map 槽或精确删除一行。引用名不带 `.dds`、`_0` 或 `.texture` 后缀。

官方普通 `.texture` 内嵌 DDS 与 Granite 编辑图的 V 方向相反。普通 `.texture` 的方向转换是强制格式规则：新建工作区时，探索器会把 WTB payload 垂直翻转到与 Granite 一致的编辑方向；“从 source 恢复 DDS”也始终恢复为该编辑方向；封回 source WTB 模板时再翻回官方方向。预览器不额外翻转显示，因此预览器、Blender、Paint.NET 和磁盘中的 DDS 朝向一致。新工作区仍会在 `workspace.json` 写入 `"DdsVerticalOrientation":"TopLeft"` 作为格式说明，但恢复和封回不再依赖该标记，旧工作区同样执行转换。普通 WTB 每次构建都实际执行 DDS 翻转和封装，不会因输入哈希等于 baseline 而隐式复制 source；因此 BC 压缩贴图的构建文件不保证与 source 逐字节相同，应以解码后的尺寸、格式、mip 和像素误差验证前后一致性。`UI-image` WTB 不套用这条普通 `.texture` 规则，继续按原始槽方向解包和封回。

旧工作区磁盘中已经存在的普通 WTB DDS 不会仅因打开工作区而被静默改写，预览器也会按文件原样显示。继续编辑或构建前，应重新生成工作区，或对相关行执行“从 source 恢复 DDS”，让文件先进入统一编辑方向；不要把旧的反向 DDS 当作新流程输入直接封回。mmat JSON 使用 2.0.0 schema 在独立检查器中查看并编码；删除 `granite_params` 后可让材质转向 `texture_maps.texture_name` 指定的普通贴图。旧 `A1/A2/A4` JSON 只能只读，必须从 `source` 重新解码后才能构建。

2026-07-28 使用全新 `pl1400` 工作区对 26 个官方普通贴图执行了强制往返审计：所有记录都实际经过编辑方向 DDS 到游戏方向 WTB 的转换，没有使用 source 直拷贝；26/26 的槽数、分辨率、DXGI BC7 格式和 mip 数保持一致。统一解码为 RGBA8 后，最坏单通道误差为 `8/255`，单张贴图最坏平均误差为 `0.069992/255`，最低 `93.9301%` 的通道值完全相同。WTB 与 payload 的 SHA-256 均不相同，这是 BC7 重编码的预期结果，不能把二进制相同作为这条流程的正确性标准。

## 3. 构建 Mod

模型文件 `.minfo/.skeleton`、全部已登记的 `.mmesh` 和 WTB/UI-image 可由编辑器构建：在工作区列表选中项目，然后在 Inspector 中使用模型的“从 unpack 复制到 build”，或贴图的封回操作。恢复按钮分别为“从 source 恢复 unpack”和“从 source 恢复 DDS”。写入后保留游戏原始相对路径：

```text
build/data/model/<类型>/<角色>/<角色>.minfo
build/data/model/<类型>/<角色>/<角色>.skeleton
build/data/model_streaming/lod0/<角色>.mmesh
build/data/model_streaming/lod1/<角色>.mmesh
build/data/model_streaming/shadowlod0/<角色>.mmesh
```

WTB `.texture`、UI WTB、mmat JSON 和 cloth XML 都会进入工作区。贴图、mmat 与 cloth 均可在编辑器中构建；Blender 插件负责编辑 CLP/CLH 并写回 `unpack` XML，C++ 编辑器负责将 XML 编码到 `build` BXM。旧 PowerShell 构建器及兼容入口已删除。

编辑器可以把 `clp`、`clh`、`sequence`、`reset` 四类 Cloth 资源分别从 `workspace.json/ClothFiles` 登记的 `unpack` XML 编码到 `build` BXM。编码在临时目录调用固定版本的 GBFRDataTools，检查 BXM 头并重新解码；回读 XML 与输入的全部元素、属性和值语义一致后才原子替换最终输出，因此失败不会破坏已有 `build` 文件。单项和批量构建都支持 Cloth。

MOT 以原生二进制作为 unpack 编辑输入。工作区列表的“动画”分类可以逐条或批量把 `AnimationFiles` 登记的 MOT 复制到 build；从 source 恢复时会先验证 `SourceSha256`，再恢复 unpack 基线。加载模型后的播放列表分别保留同一 `ModelId` 的 unpack 与 source MOT，通过来源切换预览 Blender 导出结果或原始基线；刷新工作区会重新扫描，不必重载模型。

恢复操作会把登记的 source BXM 重新解码到原来的 `unpack` XML：先验证 source BXM 哈希，再在临时目录解码并验证 XML 基线哈希；任一校验失败都不会覆盖当前 XML。恢复只重置选中的资源，不会把同组 CLP/CLH 或动作 sequence 连带覆盖，也不会写入 `build`。完成后，当前模型的 Cloth 拓扑、碰撞体和动作覆盖缓存会立即重载。

## cloth 文件组织

角色 cloth 由基础组、动作覆盖和重置列表三层组成：

Blender 侧从所选规范骨名和父子层级半隐式生成可立即精调的 CLP、开放/闭合横向网格、参数曲线及精准删除的实现契约见 [CLP 半隐式生成与精准删除](formats/CLP隐式生成与精准删除.md)。

```text
data/pl/<角色>/cloth/<角色>_0_<N>_clp.bxm   求解组 N：参数与节点拓扑
data/pl/<角色>/cloth/<角色>_0_<N>_clh.bxm   碰撞层 N：可复用碰撞体集合
data/pl/<角色>/cloth/<角色>_rmslst.bxm      动画切换时的布料重置列表
data/pl/<角色>/<角色>_<动作>_<变体>_seq_edit_cloth.bxm
                                                动画时间轴上的布料覆盖
```

### 新增 CLP 求解组的当前结论

目前应按“**高概率不能新增角色的第 9 个 CLP 求解组**”设计工具和 Mod，而不是假定只要放入一个新文件，游戏就会自动加载。这个判断尚未用运行时逆向或 `group 8` 实机实验作最终反证，因此不能写成格式层面的绝对定论；但现有资源已经给出一致且很强的限制信号：

- 角色没有 `.minfo` 一类中央清单来登记任意数量的 CLP。基础求解组只通过 `<角色>_0_<N>_clp.bxm` 的约定文件名出现。
- 对当前完整解包数据的扫描共找到 724 个 CLP，组号全部位于 `0..7`，没有任何 `_0_8_clp.bxm` 或更高组号；文件名中间的变体号也全部为 `0`。
- 玩家角色的 CLP 组号都从 0 连续排列到各自最大组号，没有中间空洞。17 个玩家角色已经完整占用 `0..7` 八组，`pl1400` 也是其中之一。
- 动作 `ClothTrack/FileId` 同样只使用 `0..7`。这更像固定的八槽编号空间，而不是可无上限扩展的文件编号。

“没有中央清单”单独来看仍可能意味着运行时按文件名探测；真正使新增组风险很高的是它与“全游戏从未出现组 8”和动作编号空间共同成立。除非以后得到运行时代码或实机反例，否则不要把新增 `pl1400_0_8_clp.bxm` 当成可用方案，也不要让构建器静默生成这种未经证实的资源。

当前 Blender/工作区链路还有一层确定限制：`workspace.json/ClothFiles` 只登记 source 中已经存在的 cloth 文件；Blender 插件只加载这些登记项，并以已有 CLP XML 为模板写回。现有 CLP 写回器不允许创建原 XML 中不存在的拓扑节点，也没有新增/删除 CLP 组或 CLP 节点的操作。因此，即使游戏侧将来证明能够发现新文件，当前工具也不能完整构造、登记和构建一个新求解组。

裙摆和袖子的实施方向应改为**复用现有 `0..7` 槽位**：保留 `<角色>_0_<N>_clp.bxm` 文件名与内部 `id_=N`，在确认不再需要原部件后，替换该槽位的节点图，或验证同一槽位能否容纳多条独立骨链。`pl1400` 的组 2 本来就是七列裙摆，最适合先用于裙子；袖子需要结合替换模型实际保留的原部件，再从其他组中选择可释放槽位。首轮只验证 CLP 骨链运动，不要求同号 CLH：CLP 与 CLH 并非一一配对，碰撞可以在基础运动成立后再接入。为支持这条路线，后续插件应新增“在已有组内创建/删除节点和连接”的能力，而不是优先实现组 8。

`_clp` 解码后的根节点是 `CLOTH`。`CLOTH_HEADER` 保存重力、空气/风阻、拉伸、局部重力、地面碰撞、移动响应和碰撞 Flags 等整组参数；`CLOTH_WK_LIST` 保存节点图。节点通过 `noUp/noDown/noSide/noPoly/noFix` 相互引用，`4095` 表示无连接。

CLP 与 CLH **不是同编号一对一配对**。CLP 是独立求解组，Header 中的 `useCollisionFlags_` 是 CLH 碰撞层位掩码：bit N 表示该求解组使用 `<角色>_0_N_clh.bxm`。同一 CLH 可被多个 CLP 复用，一个 CLP 也可同时使用多个 CLH。编辑器以 CLP 求解组为入口自动叠加掩码指定的碰撞层；CLH 下拉列表只负责检查和编辑单独的碰撞层。

当前 `pl1400` 的关联结果如下，部件名称来自节点空间、蒙皮材质和 submesh 交叉验证，不是文件内明文：

| CLP 求解组 | 节点对应部件 | `useCollisionFlags_` | 使用的 CLH |
|---:|---|---:|---|
| 0 | 十束后发 | 18 | 1、4 |
| 1 | 两束前发 | 97 | 0、5、6 |
| 2 | 七列裙摆 | 4 | 2 |
| 3 | 短侧发 | 2 | 1 |
| 4 | 长辫 | 1 | 0 |
| 5 | 身体衣物与前部挂件，仍需继续细分 | 8 | 3 |
| 6 | `a40_sheath` 刀鞘长链 | 128 | 7 |
| 7 | 胸前软变形 | 0 | 无碰撞层 |

这也解释了错误预览中“前发只有头部碰撞”的现象：旧逻辑画的是 CLP1 + CLH1，实际 CLP1 应同时使用 CLH0、CLH5、CLH6。CLH7 还引用了 CLP2 的 `_c45.._c65` 动态裙摆节点，并由刀鞘求解组6通过 bit7 使用，形成 `裙摆组2 -> 碰撞层7 -> 刀鞘组6` 的跨组依赖；这提示真实运行时存在求解顺序，不能把所有组完全并行处理。

CLP 连接目前可按拓扑关系理解：`noUp/noDown` 是同一布料链的纵向相邻节点，样本中双向互相引用；`noSide` 是相邻链之间的横向边，只保存一次方向，另一端不必再反向写一条；`noPoly` 是多边形关系。`pl1400` 中 52 条有效 `noSide` 与 `noPoly` 完全相同，说明它们共同描述布料带/布料面的横向结构，但 `noPoly` 在求解器中究竟控制四边形、剪切还是其他约束仍未证实。预览将纵向边显示为绿色、横向边显示为品红；只有 `noPoly != noSide` 时才额外用橙色显示，避免把同一条横边画两遍。横向边是布料结构约束，不是碰撞体，因此“一条横向连接”已经足以表达两个节点的关系。

> **分叉实验纠错：**官方 CLP 仍没有已知的一对多纵向样本，而且父节点只有一个 `noDown` 槽；但这不能再解释为“必须把其余子支断成新 root”。自定义骨架实机已经观察到断开次级子支会在分叉处产生拉扯。后续实验模式应允许多个子节点的 `noUp` 同时指向真实父骨，并只让父节点 `noDown` 指向指定主支；这种非互反表达尚未验证，必须明确标记并由实机对照。`noSide/noPoly` 仍属于横向约束，不应在未做独立实验时自动替代纵向分叉。

`_clh` 解码后的根节点是 `CLOTH_AT`。每条 `ClothCollision` 记录描述一个碰撞端点：`p1/p2` 是两根附着骨骼，`offset1/offset2` 是各自骨骼局部空间中的位置，`weight` 在两个变换后的位置之间插值：

```text
attachment1 = TransformPoint(BoneWorld(p1), offset1)
attachment2 = TransformPoint(BoneWorld(p2), offset2)
center      = attachment1 * (1 - weight) + attachment2 * weight
```

因此 `p1/p2` **不是胶囊两端**。端点本身以 `center + radius` 构成球；当 `capsule >= 0` 时，它引用同一 CLH 文件中另一条碰撞记录的真实 `id_`，两个记录的球心与各自半径共同构成胶囊或变半径胶囊。`capsule = -1` 表示独立球。碰撞 ID 可能不连续，动作文件和 capsule 链都必须按真实 `id_` 引用，不能用列表行号替代。编辑器会显示“球”“胶囊 -> ID”或“无效引用”，并使用动画后的完整骨骼世界变换绘制 offset。

这个结论来自现有文件的结构关联，不是官方公开的运行时代码。当前 8 组 `pl1400` 样本共有 112 条 CLH 记录：91 条 `p1 == p2` 且 `weight == 0`，另外 21 条 `p1 != p2` 全部使用非零权重；46 条记录的 `capsule` 指向同组内另一个碰撞 `id_`。例如 `_0_0_clh` 中存在 `id 1 -> 0`、`2 -> 1`、`3 -> 2` 的连续 capsule 链；`id 4 -> 0` 又横向连接另一侧端点，随后 `5 -> 4`、`6 -> 5`、`7 -> 6`。这与沿肢体串联胶囊、再用单个引用建立横向胶囊完全吻合，也说明横向胶囊不需要反向再存一条。CLP 节点自身另有由 `thick_` 决定的碰撞半径，详见 [CLP 节点碰撞半径](formats/CLP节点碰撞半径.md)。后续若从游戏运行时或更多角色样本得到反例，应以新证据修正规则。

CLH 参数的当前解释如下：`radius` 是该端点的球半径；`offset1/offset2` 是骨骼局部偏移，必须随骨骼旋转和缩放；`weight` 是双附着插值权重，不是质量或碰撞强度；`capsule` 是另一端点 ID，不是布尔形状开关；`notUseInBattle/notUseInIdle` 分别控制战斗/待机状态是否禁用。两个状态字段的切换时机仍需游戏内验证。CLP 节点的 `rotLimit` 很可能是弧度制关节摆角限制，`friction`、`thick_`、`windForceArea_` 分别对应摩擦、节点碰撞厚度和受风面积；`weight_` 更像求解权重而非直接的公斤质量。`gravityBlendRate_`、`originalRate_`、`jointScale_`、`axisAdjustRate_` 和允许缩放标志的精确公式尚未探明，编辑器不应擅自归一化或改写。

CLP 的 `no/noUp/noDown/noSide/noPoly/noFix` 与 CLH 的 `p1/p2` 使用的是**骨骼名编码**，不是 `.skeleton` 的骨骼数组下标，也不是 FlatBuffers 中的 `BoneId`。数值按十六进制转换后就是 Blender 插件导入的原始骨骼名：例如 `3141 = 0xC45` 对应 `_c45`，`545 = 0x221` 对应 `_221`。编辑器使用 `unpack/data/model/pl/<角色>/<角色>.skeleton` 验证并显示名称；覆盖 Blender 导出的新骨架后需点击“刷新”或重新加载预览。它不会混用可能出现重名的 fp/wp 骨架，未命中的引用会明确保留原始编码。

当前 `pl1400` 样本中，CLP 的 175 个不同骨骼引用与 CLH 的 38 个不同端点引用都能在 `pl1400.skeleton` 中找到。骨骼名 `_xxx` 是游戏原始标识；Blender 插件中的“Translate Bones”只会把一部分通用人体骨骼另行翻译为 `Hips/Chest/Head` 等便于阅读的别名，cloth 专用骨骼通常仍保留 `_c45` 这类名字。

自定义骨架不能沿用“raw ID 能在某张名称表中解释就算有效”的宽松规则。2026-07-27 的 `pl1400.004` 审计发现 CLP2 有 165 条节点记录已失去真实 `bone_ref`；它们在 Blender/预览器视口中不可见，却仍被 XML/BXM 保存，并包含会撞入 humanoid 编号空间的值。Blender 的“检查并清理无效节点/连接”只按当前 Armature 的真实 Bone 对象删除这类记录和悬空边；节点列表减号则精确删除当前行。最终导出要求所有非空 CLP/CLH 骨引用都能从真实对象映射到本次 skeleton，否则阻止写回。

编辑器内使用 Blender 插件 v2 映射的首选 humanoid 名称，并在括号内保留游戏原名，例如 `Hips (_000)`、`Brow_01_L (_830)`、`Tongue Tip (_8c2)`；映射覆盖身体、手指、眼睛、眼睑、眉、嘴唇、牙齿和舌头，没有映射的骨骼仍显示 `_c45`。这只改变显示与下拉选项，保存时仍写入原始骨骼编码。

在 `Skeleton & Cloth` 面板中，左侧骨骼列表会与视口拾取联动；右侧 `Cloth 物理` 页按 CLP 求解组和 CLH 碰撞层显示节点、骨骼附着、形状与连接。当前可写回 CLH XML 的字段是 `radius/weight/offset1/offset2`；碰撞 ID、`p1/p2`、capsule 链和状态标记仍只读，避免在引用约束未完整验证前破坏数据。

动作覆盖文件的 `Seq/ClothTrack` 记录使用 `FileId` 指向 0–7 编号空间；当记录携带 `CollisionId0..N` 时，ID 均能在 `FileId` 对应的 CLH 碰撞层中找到。记录在 `StartTime` 应用 `ScaleRate`、`FadeInFrame`、`FloorAdditiveOffset` 等覆盖。`StartTime` 基本位于 60 FPS 帧网格上。实际数据中 `ScaleRate` 可出现 `0`、`2.6`、`97`、`100`，编辑器不能把它限制在 `0..1`。

`pl1400` 的 43 个 `seq_edit_cloth` 全部能一一匹配同名 MOT，共含 229 条覆盖记录；单个动作最多同时操作 5 个 FileId。它们更像动作期间对常驻求解组和碰撞层做定时覆盖，而不是临时拼装基础文件。对全部 524 个 MOT 的扫描还发现：0–5 与 7 组普遍存在 cloth 骨骼轨道，主要是旋转目标，其中裙摆组2的帧间变化最密集；刀鞘组6仅在一个 MOT 中出现常量轨道，基本依赖物理解算。当前更合理的执行模型是 MOT 先给出 cloth 骨骼目标姿态，再由 CLP 参数、拓扑和选中的 CLH 层进行二次修正。`originalRate_` 很可能参与回到动画原姿态的混合，但精确公式仍需运行时验证。

`SeqFlag=0` 的记录主要携带碰撞与 Scale 覆盖；当前样本中 `SeqFlag=1/3` 没有碰撞引用，主要改变地面附加偏移。两个 Flag 的精确运行时位含义仍需游戏内验证。`RESET_MOT_LIST` 则列出需要重置布料状态的动作切换。

因此目前能确定的是“某动画在某时刻引用并覆盖了哪些 CLH `FileId` 及其中哪些 Collision ID”，还不能把每条记录简化成已确认的碰撞层布尔开关。预览器选中身体 MOT 时会自动读取同名 `_0_seq_edit_cloth.bxm.xml`，显示 CLP `useCollisionFlags_` 给出的“基础 CLH”、动画中带有 Collision ID 的“动画引用 CLH”、所有 `FileId` 事件层，以及当前时间已触发的记录。展开 `Cloth 动画覆盖` 可查看时间、`SeqFlag/LayerFlag`、Collision IDs、Scale、淡入帧和地面偏移；不含 Collision ID 的记录保持标记为 `FileId` 事件，不会被误报成碰撞层启用。

BXM 是大端序二进制 XML：16 字节头后依次为扁平节点表、键值偏移表和去重字符串池。官方 [GBFRDataTools](https://github.com/Nenkai/GBFRDataTools) 可在 BXM/XML 间语义往返；重建后的基础文件可能因去重策略不同而变大，但再次解码的 XML 内容一致。

模型输出路径保持游戏结构：

```text
build/
  data/
    model/<类型>/<角色>/*.minfo
    model/<类型>/<角色>/*.skeleton
    model_streaming/lod#/*.mmesh
    model_streaming/shadowlod#/*.mmesh
```

`build/` 可以直接作为 Mod 根目录使用，但要先确认本次 Mod 只需要当前已支持构建的模型文件。

## 目录与能力边界

仓库目录职责见 [C++ 架构](架构.md#目录)。当前工作区生成可自动解码普通 WTB 和角色 UI WTB 为 DDS、mmat 为 JSON、cloth BXM 为 XML，并从 Granite GTS/GTP 提取 `albd/msk1/msk2/nrml/conj/iris/eyeh`。已有 WTB 可按源模板反向封回，也支持新建普通 `.texture`；mmat 与 cloth 均可编码，Blender 插件继续负责 CLP/CLH 的可视化编辑和 XML 写回。

当前可构建的最终资源包括 `.minfo/.skeleton`、全部工作区 LOD `.mmesh`、普通 WTB/UI-image、mmat，以及 Blender 插件写回的 cloth BXM。C++ 预览器可按工作区中的具体 `.mmesh` 切换普通/阴影 LOD，并在视口与 Inspector 标出多 Mesh 分段、4/8 权重、UV1 和顶点色能力。

工作区大列表使用 Dear ImGui 原生多选：普通点击切换单项，`Ctrl` 增减选择，`Shift` 选择连续范围，也支持框选与 `Ctrl+A`。Inspector 和“快捷操作”会在多选时切换为批处理，可批量构建、恢复及清除所选 mmat 的 `granite_params`；“构建全部修改项”会构建所有可用且已修改的资源，包括 cloth XML。
